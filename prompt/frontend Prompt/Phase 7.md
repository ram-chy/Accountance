# Accountance Frontend — Phase 7: Cash & Bank Management UI

## 1. Objective

Implement **Phase 7 — Cash & Bank Management UI** in the existing Accountance
Accounting Web App.

Build on the completed frontend foundation from Phases 0–6 and the existing
Laravel accounting backend.

The goal is to provide a clear, reliable interface for managing cash and bank
accounts and their supported transactions, while preserving the backend's
double-entry accounting rules.

Potential functionality to verify and implement where supported:

- View cash and bank accounts.
- View account details and available balance information.
- View transaction history.
- Search and filter transactions.
- Create supported cash/bank transactions.
- View transaction details and status.
- Display the accounting journal generated by a transaction, if the API exposes
  it.
- Show loading, empty, error, validation, and mutation states.
- Respect company context and permissions.

**Scope boundary:** this phase is for Cash & Bank Management. Do not implement
bank reconciliation, general ledger screens, financial reports, or unrelated
business modules unless the existing blueprint explicitly assigns them to
Phase 7. Do not invent missing backend capabilities.

Stop after Phase 7.

## 5. Cash & Bank overview

Build an overview screen using verified backend data.

Include the following only where the API provides reliable data:

- Cash accounts.
- Bank accounts.
- Account code and name.
- Account subtype.
- Active/inactive status.
- Available or ledger balance.
- Currency information.
- Navigation to account details and transaction history.

### Balance integrity

- Never fabricate account balances.
- Do not assume an account's configured currency is the company's default
  currency.
- Do not add amounts across currencies without a verified conversion mechanism
  and exchange-rate policy.
- Use existing exact-decimal utilities for money.
- Do not use JavaScript floating-point arithmetic for financial calculations.
- Distinguish a ledger balance from an available bank balance if the backend
  exposes different concepts.
- Do not label a balance as current, available, reconciled, or cleared unless
  the source data supports that meaning.
- Display the balance's as-of date or relevant context when provided by the API.

If no suitable aggregate endpoint exists, do not create a frontend approximation
that makes unsupported completeness claims. Prefer an accurate account list with
individual balance information, or document the limitation.

## 6. Cash/bank account list and details

Implement an account list with the supported filters and fields.

Where available, display:

- Account code.
- Account name.
- Cash or bank classification.
- Associated chart-of-accounts entry.
- Currency.
- Active status.
- Balance.
- Relevant transaction actions.

Account details should display the verified account information and transaction
history.

Requirements:

- Use server-side filters where the API supports them.
- Use the actual response pagination contract.
- Never fabricate totals or claim a complete result set when only one page was
  fetched.
- Provide loading, empty, error, and retry states.
- Handle inactive accounts consistently with backend rules.
- Prevent stale account data from remaining visible after a company switch.

If account creation, editing, activation, or deactivation is supported,
implement only the verified operations and permissions. Do not duplicate
chart-of-accounts functionality unnecessarily.

## 7. Transaction list and history

Implement a transaction list using the real backend transaction resource.

Display only fields available from the verified API, potentially including:

- Transaction reference or number.
- Transaction date.
- Cash/bank account.
- Transaction type.
- Direction or transaction category.
- Description.
- Amount.
- Currency.
- Status.
- Counterparty or related reference, if supplied.
- Related journal reference, if available.

Support only verified filters, such as date range, account, transaction type,
status, or search.

Requirements:

- Filters must apply to the full server-side dataset when supported by the API.
- Reset pagination when filters change.
- Debounce search where appropriate and cancel obsolete requests.
- Use exact-decimal formatting.
- Clearly distinguish debit/credit or money-in/money-out semantics according to
  the backend contract.
- Do not infer a transaction's effect on an account balance from its label
  alone.
- Display server-provided transaction status without inventing additional
  states.
- Provide accessible loading, empty, and error states.

Do not implement an unverified client-side transaction ledger.

## 8. Transaction creation and lifecycle

First inspect which transaction operations the backend actually supports.
Implement only those workflows.

Possible operations to investigate include:

- Money received into a cash/bank account.
- Money paid out.
- Transfers between cash/bank accounts.
- Other explicitly supported transaction categories.

Do not assume every category is supported.

For each implemented form:

- Use verified request fields and validation constraints.
- Select accounts through the existing secure API helpers.
- Respect account eligibility rules.
- Use appropriate date, amount, description, reference, and counterparty fields
  only when supported.
- Apply exact-decimal handling.
- Map HTTP 422 field errors back to the relevant controls.
- Display general errors without leaking stack traces or internal details.
- Prevent duplicate submissions.
- Preserve entered data after recoverable failures.
- Do not automatically retry financial mutations.

If the backend has a draft/posted lifecycle, represent it accurately. If
transactions are immediately posted, do not fabricate a draft state.

If transfers are supported, follow the backend's actual transfer model. Do not
implement a transfer as two independent, unrelated requests if the backend
provides an atomic transfer operation.

Never create accounting journal entries directly from the browser. Use the
verified backend transaction endpoint and let the backend enforce double-entry
accounting.

## 9. Related journals and Phase 6 integration

Reuse the existing journal module where appropriate.

If a transaction resource exposes a related journal:

- Display the verified journal reference and status.
- Provide a link to the journal detail route where safe and supported.
- Do not duplicate the journal posting engine.
- Do not expose edit or delete controls for posted journals.
- Do not assume all cash/bank transactions create journals unless the backend
  confirms this.

### Journal source-type follow-up

The Phase 6 report identified a backend follow-up concerning
`CashBankTransaction` as a journal source type.

Inspect the current backend enum, journal resource, and tests before changing
the frontend.

- Do not add `CashBankTransaction` to the frontend enum merely because the
  earlier report recommended it.
- Do not change the Laravel backend in this phase.
- If the backend already exposes the new value, reflect it in the frontend
  validator and source badge.
- If it does not, preserve safe fallback rendering for unknown source values and
  document the backend follow-up.

## 10. Permissions and authorization

Inspect the real permission enum, policies, route middleware, and role matrix.

Use the exact verified permissions for:

- Viewing cash/bank accounts.
- Viewing transactions.
- Creating transactions.
- Editing, cancelling, deleting, or posting transactions, if supported.
- Viewing related journals.

Do not guess permission names or assume that `accounts.view`, `journals.view`,
and cash/bank permissions are interchangeable.

The UI may hide unavailable actions, but the backend remains the authority for
authorization.

Handle forbidden responses safely. Where permission is missing, avoid making
unnecessary requests.

## 11. Secure API and company isolation

All browser requests must use the existing same-origin proxy and approved API
helpers.

- Never call Laravel directly from browser components.
- Never expose the JWT, session secret, or server-held company context.
- Do not bypass the proxy allowlist.
- Do not trust a company ID supplied by the browser.
- Do not implement client-side accounting writes.

Follow the established no-query-cache approach unless inspection demonstrates
that the existing architecture has changed.

Company-switch requirements:

- Key requests and state to the active company.
- Abort obsolete requests.
- Discard responses from a previous company.
- Reset account, transaction, and form state when company context changes.
- Do not display the previous company's transactions under the newly selected
  company.
- Do not issue unscoped requests when no company is active.
- Never submit a pending form under a different company from the one in which it
  was opened.

Add explicit company-switch isolation tests.
